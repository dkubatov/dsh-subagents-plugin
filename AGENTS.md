# AGENTS.md — инструкции для агентов

Этот файл обязателен для любого агента (человека или модели), который меняет
этот репозиторий. Сначала прочитайте его, затем — `README.md`,
`COMPATIBILITY.md`, `PLAN.md` и README пакета
[`packages/dsh-subagent-codex-next`](packages/dsh-subagent-codex-next/README.md).

## 1. Ветки и pull request — обязательный процесс

**Прямые коммиты и `git push` в `main` запрещены.** Каждая задача — отдельная
ветка от актуального `main` и отдельный PR. Это относится и к правкам
документации, и к версиям пакета, и к «однострочным» фиксам.

Запрет действует и на уровне GitHub: ruleset **`main: pull requests only`**
(активен, без bypass-акторов) требует PR для `main`, запрещает force-push и
удаление ветки; прямой `git push origin main` будет отклонён GitHub.

### HUMAN APPROVAL: ветка, её имя и PR

Перед созданием ветки и перед открытием PR агент обязан получить **явное
одобрение человека**. Это два отдельных чекпоинта:

1. **Ветка и её имя.** Предложите тип, имя (`<type>/<short-slug>`), цель
   задачи и какие файлы будут затронуты. Дождитесь явного «да/ок/approve»;
   без ответа ветку не создавайте. Одобренное имя не меняйте без нового
   согласования.
2. **Pull request.** После коммита покажите человеку заголовок PR, краткое
   summary изменений и выполненные проверки — и получите **отдельное**
   одобрение на открытие PR. Одобрение ветки не означает одобрение PR.
3. **Независимое ревью.** Перед merge PR обязан пройти **независимое
   положительное ревью**. Ревьюер — не автор изменений: Codex Review в этом
   репозитории, другой человек или агент. Merge разрешён только когда ревью
   завершено и не содержит unresolved findings; замечания исправляются в той
   же ветке, после чего PR пере-ревьюится. Нельзя сливать по self-review, «по
   молчанию» или с открытыми замечаниями; закрывать review-треды без
   исправления нельзя.
4. **Merge.** Только после зелёных проверок, одобрения PR и **независимого
   положительного ревью** (или отдельного одобрения merge, если так
   договорились).

Если ответа нет — остановитесь и ждите. Нельзя «на всякий случай» создавать
ветку/PR, менять согласованное имя или переносить коммиты в `main` в обход PR.

1. Обновите `main`:

   ```powershell
   git switch main
   git pull --ff-only
   ```

2. Создайте ветку с префиксом типа задачи:

   ```powershell
   git switch -c <type>/<short-slug>
   ```

   Допустимые `<type>`: `feat`, `fix`, `docs`, `chore`, `test`, `ci`.
   `<short-slug>` — 2–5 слов через дефис, например:
   `docs/agents-md`, `fix/preset-override-render`, `feat/codex-0-170-probe`.

3. Сделайте изменения и прогоните проверки из раздела 4.

4. Коммитьте в свою ветку (Conventional Commits, тема на английском):

   ```powershell
   git add -A
   git commit -m "docs: add AGENTS.md with branch and PR rules"
   git push -u origin HEAD
   ```

5. Откройте PR:

   ```powershell
   gh pr create --title "docs: add AGENTS.md with branch and PR rules" --body "Описание изменения и проверок"
   ```

6. После проверки PR сливается **через GitHub** (squash), а ветка удаляется:

   ```powershell
   gh pr merge --squash --delete-branch
   git switch main
   git pull --ff-only
   ```

Правила:

- один PR — одна задача; не смешивайте фикс, рефакторинг и обновление версии;
- не делайте force-push в `main`; в ветке PR допустим только
  `git push --force-with-lease`;
- если GitHub-доступа нет (например, локальная проверка) — всё равно работайте
  в отдельной ветке и оставьте её готовой для PR, не переносите коммиты в
  `main` вручную;
- если PR не проходит проверки — исправляйте в той же ветке, не открывайте
  новый PR на ту же задачу.

## 2. Что это за репозиторий

Публичный форк Codex-провайдера субагентов для DeepSeek Harness (DSH).
Пакет [`dsh-subagent-codex-next`](packages/dsh-subagent-codex-next/) —
это `@deepseek-ai/dsh-subagent-codex@0.2.2-rc.5` с заменённым Codex-payload:
вместо `@openai/codex@0.153.4` (ломается на `gpt-6.x`) используется
`0.166.0`. Протокольный адаптер upstream не менялся; добавлены опции
`codexPackage`, `codexBin`, `command`.

Любое изменение пакета должно сохранять это свойство: **Codex-адаптер
(JSON-RPC) остаётся upstream-кодом**, меняются только pin, конфигурация и
диагностика.

## 4. Проверки (Definition of Done)

Перед PR выполните применимые пункты.

- **Код пакета:** `node --check packages/dsh-subagent-codex-next/lib/index.js`
- **Сборка tarball'а:** `cd packages/dsh-subagent-codex-next; npm pack --pack-destination .artifacts`
  (tarball должен собраться; артефакты в `.artifacts/` не коммитятся).
- **Handshake без токенов:** `node scripts/probe-app-server.mjs --no-turn`
  (после `npm install` в каталоге пакета; 0 вызовов модели) — ожидается
  `outcome=handshake-only`.
- **Модельный probe** — только если изменение касается Codex payload,
  протокола или конфигурации провайдера. Использует реальный ChatGPT-аккаунт:
  `node scripts/probe-app-server.mjs --model gpt-6-luna` (и `gpt-6.1-sol`,
  `gpt-6.1-terra`). Пишите результат в `COMPATIBILITY.md`; логи в
  `scripts/logs/` не коммитятся.
- **YAML/патчи:** проверьте синтаксис YAML-парсером; изменения профиля
  `~/.dsh` и `~/.codex` в репозиторий не попадают.
- **Документация:** обновите `COMPATIBILITY.md` при изменении проверенных
  версий и `PLAN.md`/README — при изменении поведения и установки.
- **Гигиена:** `node tools/scan-hygiene.mjs` — 0 findings (нет локальных
  путей и секретов); см. раздел 10.

PR описывает: что изменено, какие проверки выполнены, какие версии DSH/Codex
затронуты.

## 5. Чего нельзя делать

- коммитить в `main` напрямую и пушить туда (см. раздел 1);
- коммитить `node_modules/`, `.artifacts/`, `local-backups/`, `scripts/logs/`,
  `scripts/results/`, сгенерированные JSON-схемы и локальные копии профиля;
- коммитить секреты, токены, `auth.json`, содержимое `~/.codex` и личные пути
  пользователя вне примеров;
- менять пин `@openai/codex` без новой записи в `COMPATIBILITY.md` и прогона
  probe: `0.170.0` не проверен, `0.166.0` — проверенный baseline;
- менять живой профиль DSH (`~/.dsh/profiles/…`) и `~/.codex` в рамках задач
  этого репозитория без явной просьбы владельца: профиль — пользовательская
  конфигурация;
- публиковать пакет в npm без явной просьбы, `npm login` и успешного
  live-теста.

## 6. Релиз пакета

Схема версии: `<upstream DSH version>-dsh.<n>` (например,
`0.2.2-rc.5-dsh.2`). Зависимости и peers пакета **точно** соответствуют
версии хоста, для которой он собран; новый хост — новый релиз.

Порядок:

1. bump `version` в `packages/dsh-subagent-codex-next/package.json`;
2. обновить README/COMPATIBILITY/PLAN (ссылки на релиз, проверенные версии);
3. `npm pack --pack-destination .artifacts`, пересчитать `SHA256SUMS.txt`;
4. изменения — через ветку и PR (раздел 1);
5. после merge — GitHub Release:

   ```powershell
   gh release create v<version> <tarball> <SHA256SUMS> --title "..." --prerelease --notes-file <notes>
   ```

6. npm-публикация — только после успешного live-теста и `npm login`
   владельца: `npm publish --tag next` (prerelease-версию не помещать в `latest`).

## 7. Ключевые технические факты

- Upstream-плагин байт-идентичен во всех опубликованных версиях и всегда
  пинит `@openai/codex@0.153.4`; именно этот билд отдаёт
  `HTTP 400 model_not_found` для `gpt-6.x` при ChatGPT-аккаунте.
- Wire-последовательность плагина проверена на `0.166.0` и
  `0.169.0-alpha.11.1`: правки JSON-RPC не требуются (см.
  `spikes/protocol/REPORT.md`).
- DSH `0.2.2-rc.5`: delegation tools штатно preset-scoped (shipped `standard`
  preset содержит `subagent`/`subagent_fork`, а базовые Host-строки
  `tool-subagent` web-bundle выключает), **но** плагин может добавлять свои
  Host-строки `tool-subagent` — они работают, если
  `@deepseek-ai/dsh-tool-subagent` резолвится в совместимую rc.5-версию.
  Главная ловушка: не оставляйте в профиле upstream
  `@deepseek-ai/dsh-subagent-codex@0.2.2-rc.1` — его зависимость
  `@deepseek-ai/dsh-tool-subagent@0.2.2-rc.1` затеняет rc.5 и отключает **все**
  строки `tool-subagent`. Подробности — `COMPATIBILITY.md`,
  `research/live-e2e-2026-11-19.md`.
- Schemastery материализует отсутствующий массив `command` как `[]`; в
  `apply()` пустые `command`/`codexBin` нормализуются в `undefined` — не
  ломайте это поведение.
- Удаление override `preset-standard` (миграция со старой preset-схемы)
  требует **полного перезапуска DSH**: HMR обновляет Host-строки, но не
  пере-активирует preset-реестр.
- `probe-app-server.mjs` повторяет ровно ту JSON-RPC последовательность, что
  использует провайдер; `--no-turn` не вызывает модель.

## 8. Коммиты и язык

- Conventional Commits, тема на английском: `fix: …`, `docs: …`, `feat: …`.
- Документация в репозитории — на русском; код, package.json, commit subject —
  на английском.
- В PR указывайте, какие проверки выполнены и что осталось непроверенным;
  не выдавайте диапазон `engines.dsh`/peers за протестированные версии.

## 9. Перезапуск DSH: сообщайте явно

Если действие требует перезапуска DeepSeek Harness (изменение профиля,
`cordis.patch.yml`/preset, установка или обновление плагина без HMR,
обновление хоста, проверка композиции «с нуля»), агент обязан **прямо написать
это в ответе**, а не оставлять пользователя догадываться.

Формат обязательного сообщения:

- маркер в начале или конце ответа: **ТРЕБУЕТСЯ ПЕРЕЗАПУСК DSH**;
- что перезапустить: приложение целиком (не только сессию/чат), включая трей,
  дождаться полного выхода процесса;
- зачем: что именно не применится без рестарта (например, preset-реестр или
  новая композиция);
- что сделать после: новая сессия/чат и какая проверка подтвердит успех;
- как откатить, если после рестарта что-то сломается (бэкап/команда).

Нельзя выдавать «новую сессию» за достаточное условие, если нужен рестарт
процесса: HMR обновляет Host-строки, но не пере-активирует preset-реестр и не
пересобирает композицию с нуля. Если не уверены, нужен ли рестарт, — так и
напишите: «вероятно, потребуется рестарт; проверю после новой сессии».

## 10. Локальные пути и секреты: запрещено

**Ни в одном месте репозитория нельзя указывать реальные локальные пути или
секреты.** Это относится к коду, конфигурациям, документации, комментариям,
коммитам, pull request'ам, отчётам, логам, JSON/JSONL-артефактам и ответам
агента.

Запрещено:

- реальные домашние/машинные пути: `C:\Users\<name>…`, `%USERPROFILE%`-выводы,
  `AppData\Local\…`, абсолютные рабочие каталоги этой машины
  (`<буква>:\…`), пути установки приложения, build-хэши каталогов;
- секреты и учётные данные: access/refresh-токены, API-ключи, пароли, cookies,
  `auth.json`, приватные ключи, URL с токенами, содержимое `.env`;
- вывод команд, который печатает такие пути или секреты, если он попадёт в
  репозиторий, отчёт или ответ пользователю.

Как надо:

- использовать плейсхолдеры: `<HOME>`, `<DSH_HOME>`, `<DSH_PROFILE_DIR>`,
  `<DSH_INSTALL_DIR>`, `<DSH_NODE_EXECUTABLE>`, `<CODEX_CLI_PATH>`,
  `<workspace>`, `<repo>`, `<path>`;
- скрипты должны принимать пути аргументами или брать их из `DSH_*`/стандартных
  переменных окружения, а не хардкодить;
- генерируемые артефакты (снимки версий, логи probe) санитизировать **до**
  коммита: `tools/collect-versions.mjs` уже пишет плейсхолдеры;
- перед коммитом и PR запускать `node tools/scan-hygiene.mjs` и устранять все
  findings;
- если секрет всё-таки попал в коммит: не просто удалить — сообщить владельцу,
  ротировать секрет и отдельно решить вопрос переписывания истории (обычный
  PR этого не исправляет).

Исключение одно: примеры с явными плейсхолдерами (`C:\Users\<you>`,
`<DSH_INSTALL_DIR>`), а также публичный автор проекта/URL GitHub — это не
локальные пути.

## 11. Делегирование субагентам: когда, кого, с каким усилием

Основной агент (root) делает работу сам. Субагент — **исключение, а не
норма**: лимит активных субагентов — **4**, глубина делегирования — **не
больше 2**, и эти лимиты не являются целью.

### 11.1. Когда делегировать (только эти три случая)

1. **Параллелизм**: ≥2 независимых кусков работы, которые реально ускоряют
   результат; у каждого — своя область/файлы, пересечений записи нет.
2. **Изоляция контекста**: шумная объёмная работа (десятки файлов, логи, вывод
   команд), которую не нужно тащить в контекст root.
3. **Независимая проверка**: нужно мнение другой модели/семьи (review,
   adversarial check) на результат.

Если ни один случай не выполняется — **не делегировать**.

### 11.2. Запрещено делегировать

- одну небольшую задачу (<3–5 tool-call'ов), которую root сделает сам;
- последовательную работу с зависимостями и общим контекстом;
- интеграцию, финальную сборку и финальный ответ;
- задачи, которым нужен незавершённый контекст root;
- «на всякий случай», для демонстрации или чтобы «казалось параллельно».

### 11.3. Ростер и усилия

| Исполнитель | Модель / усилие | Роль |
|---|---|---|
| root (сам) | DeepSeek-V4.1-Flash (`deepseek-flash`): `high` по умолчанию, `off`/`low` для механики, `max` — редко | вся работа по умолчанию |
| root, вручную | ASTRA (`gpt-6.2-astra`/`gpt-6-astra`): `high`/`xhigh` | **только** ручное переключение main пользователем |
| `subagent_codex` | gpt-6-luna / `medium` | дешёвый воркер: параллельный сбор/чтение, механические подзадачи |
| `subagent_codex_luna` | gpt-6-luna / `medium` | алиас предыдущего; предпочитать базовый инструмент |
| `subagent_codex_sol` | gpt-6.1-sol / `medium` | обычный кодинг/исследование, когда нужен Codex-агент |
| `subagent_codex_terra` | gpt-6.1-terra / `medium` | визуал/UI/скриншоты/computer-use |
| `subagent` / `subagent_fork` (если смонтированы) | DeepSeek flash: `off`/`low`/`high`/`max`, `high` по умолчанию | нативные DeepSeek-субагенты; `subagent_fork` — с контекстом |
| ASTRA как субагент | — | **запрещено** |
| DeepSeek-V4-Pro | — | **не использовать** (retired; запросы к `deepseek-v4-pro` роутятся на flash) |

Внешние `subagent_codex*` — листовые воркеры: они не порождают субагентов и
не принимают follow-up; каждый вызов — ровно одна задача и один ответ.
Нативные `subagent`/`subagent_fork` могут принимать follow-up; `subagent_fork`
наследует контекст.

### 11.4. Усилия

- Субагентам по умолчанию — `medium`; `high` — только после провала
  `medium`, не заранее.
- `xhigh`/`ultra`/`max` субагентам не выдавать: это дело root или ручного
  переключения main на ASTRA.
- Усилие — не способ исправить плохой промпт: сначала уточнить задачу и
  критерии приёмки.
- Шкалы моделей не сравнивать 1:1: DeepSeek — `off`/`low`/`high`/`max`,
  GPT — `low`/`medium`/`high`/`xhigh`/`max`/`ultra`.

### 11.5. Эскалация

1. root DeepSeek `high` → root DeepSeek `max` (без нового агента);
2. нужен другой уровень/семья → `subagent_codex_sol` `medium`, при провале —
   `high`;
3. ASTRA — только после **ручного** переключения main пользователем; root
   может работать на ASTRA сам, но не отдаёт её субагенту и не просит включить.

### 11.6. Параллелизм и изоляция

- Не более 4 активных субагентов одновременно; типично 0–2.
- Каждому — непересекающиеся файлы/область; для параллельных правок в коде —
  отдельные worktree/ветки.
- root владеет интеграцией, финальными проверками и ответом пользователю.
- Контракт вызова: цель, границы (файлы/что нельзя трогать), критерии
  приёмки и тесты, формат результата; без этого вызов запрещён.

### 11.7. Учёт

- Логировать/учитывать: инструмент, модель/усилие, стоимость/время, принят ли
  результат.
- Раз в месяц пересматривать ростер по фактам: если `medium` стабильно
  справляется — `high` не звать; если DeepSeek flash справляется — GPT не
  звать.
- Жёстких runtime-guards на «надобность» нет: это дисциплина в этом файле плюс
  лимиты `maxActiveSubagents = 4` и `maxDepth = 2`; отдельный enforcement —
  отдельная задача (плагин/guard).
